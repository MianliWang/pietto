## 结论

`BLOCKED`：不 `READY_FOR_FOCUSED`，不 `READY_FOR_DB`。

## R1 — MySQL `lpad` 的 bound occurrence 修复只扩展了观察，未建立可渲染的逐 occurrence leaf

修复将 `rendered_tree_nodes(..., family)` 及 `rendered_value_nodes(..., family)`
在 MySQL `lpad` 上扩展为 `(0, 1, 0, 0, 1, 2)`，这正确反映
`CASE WHEN CHAR_LENGTH(s) >= width THEN s ELSE LPAD(s, width, fill) END`
的实字节访问序列。但完整链仍有两个断口。

1. **初始 bound-literal 分配仍未按该序列进行。**
   `project_sql_emission_ast.py` 的 `collect()` 调用
   `rows.rendered_constant_chains(plan, reference)`，而该函数仍没有 `family`
   参数，内部调用的是 `rendered_tree_nodes(plan, reference)`。因此对 bind-safe
   literal，它只产出 authored tree 的一次 width/text chain；`occurrences` 与
   `allocate_uses()` 没有第二次 `NativeUse`。这正是 candidate 所称已修复、但仍
   留下的 MySQL `?` 少参根因。

2. **即使只给 `rendered_constant_chains` 补 family，现有值模型仍无法保留第二条 use。**
   `build_row_value()` 对 `ProjectSQLScalarCall.arguments` 每个 argument 只建一次
   value；`parameters.build_value()` 从 `uses[original.ref]` 取一条 use，并冻结在
   一个 `SQLParameter` 上。renderer 随后两次渲染同一 operand/object，不能从 deque
   取得第二条 use。若 allocation 产生两条 use，第二条成为无 leaf 的残留；
   `row_parameter_leaves()` 会按 family 再次看到同一 `SQLParameter` 两次，而
   `verify_row_parameters()` 和 compiled verification 都要求每次 leaf 对应其自己的
   `use`。因此当前补丁既不能发出正确的 MySQL arguments，也不能仅靠增加 use
   通过 verifier。

这必须以一个 canonical occurrence representation 修复：MySQL `lpad` 的每一个
实渲染 parameter marker 必须有独立且有序的 leaf/use，renderer、`parameter_uses`、
`native_arguments()`、compiled rebuild 和 verifier 都从同一序列消费。不能只在树
遍历层重复引用，或在 execution 层补复制参数。

所需 focused witness 至少应为 bind-safe MySQL project 的直接/inline `lpad`，其中
可绑定 Text 或 Int 位于实际重复的 `s`/`width` 位置（conditional width + Unicode
fill）。必须断言：

- rendered SQL `?` 的精确顺序和数目；
- `artifact.parameter_uses` 的逐 occurrence ordinal/server index/slot；
- `native_arguments()` 的值序列及重复；
- public canonical decoder、normal verifier、compiled load/re-emit 和 live template
  对同一 inventory 均成功。

当前测试仅断言 `template.slots == [Text, Int, Int]` 与 compiled SQL equality；两者
都不能证明重复 MySQL marker 的 use/argument 完整性。

## R2 — family 传播仍遗漏三个实际 consumer，public/template 的 actual-order inventory 不闭合

除 R1 的 `rendered_constant_chains` 外，以下调用者仍默认 `family=None`，因此在
MySQL `lpad` 上退回 authored 三 operand 遍历：

- `project_sql_emission_ast.value_requirements()`：生成的 requirement inventory
  不是实际渲染 occurrence inventory；
- `project_sql_emission_verification.verify_row_generated_requirements()` 中的
  `node_expectations()`：独立 verifier 与 builder 同步遗漏，不能成为独立 closure；
- `project_sql_emission_ast.row_binding_obligations()`，以及
  `project_execution_binding_verification._discharged()` 对它/`spliced_value_nodes()`
  的调用：template binding obligation image 不是实际 MySQL rendering order。

`row_parameter_leaves()` 已传 `query.request.family`，pure/public parameter-token
检查也要求 parameter event、leaf 和 `parameter_uses` 等长。因此这些遗漏不会安全地
放宽为可执行；相反，它们证明当前 builder、public decoder、compiled verifier 和
template 并非以一个完整 occurrence authority 收敛。R1 修复必须同时消除这些
family-less actual-order caller，避免 builder/verifier/pure 两两同错。
